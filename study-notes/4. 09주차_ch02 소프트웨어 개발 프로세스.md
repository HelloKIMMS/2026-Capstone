## 01. 소프트웨어 개발 프로세스의 이해

### 프로세스란?
- **일을 처리하는 과정 또는 순서**
- 주어진 일을 해결하기 위한 목적으로, 그 순서가 정해져 수행되는 일련의 절차
- 예시: 공장 조립 공정, 요리 레시피, OS 설치 화면 안내 등

### 프로세스의 목적
- 이전에 얻은 **노하우 전달** → 시행착오 감소 → 빠르게 적응
- **가이드(guide) 역할** 수행

### 프로세스의 3요소
| 요소 | 설명 |
|------|------|
| 인원 | 능력, 교육 및 동기가 부여된 사람 |
| 프로세스 | 작업들의 관계를 정의하는 절차와 방법 |
| 도구와 장비 | 개발에 사용되는 툴 및 장비 |

## 02. 소프트웨어 프로세스 모델의 이해

### SDLC (Software Development Life Cycle)
- 소프트웨어 **개발 생명주기**
- SW를 어떻게 개발할 것인가에 대한 전체적인 흐름을 체계화한 개념
- 개발 계획 수립부터 최종 폐기 때까지의 전 과정을 다룸
- 순차적인 단계로 이루어짐

### 소프트웨어 프로세스 모델의 목적
- 소프트웨어 개발의 전 과정을 하나의 프로세스로 정의
- 주어진 예산과 자원으로 개발하고 관리하는 방법을 구체적으로 정의
- **고품질의 소프트웨어 제품 생산**을 목적으로 함

## 03. 주먹구구식 모델 (Build & Fix Model)

> 별칭: Code and Fix 모델, 즉흥적 소프트웨어 개발 모델

### 개요
- 공식적인 가이드라인이나 프로세스가 **없는** 개발 방식
- 요구 분석 명세서나 설계 단계 없이 간단한 기능만 정리하여 개발

### 개발 단계
```
코딩(구현) → 제품 → 문제? → [아니오] → 사용
                  ↑              |
                  └── [예] 수정 ──┘
```

### 적합한 상황
- 개발자 한 명이 **단시간**에 마칠 수 있는 경우
- 대학 수업의 한 학기용 소규모 프로젝트 정도

### 단점
- 정해진 개발 순서나 문서화된 산출물이 없어 **관리 및 유지보수가 어려움**
- 프로젝트 전체 범위 파악 불가, 좋은 아키텍처 설계 불가
- 업무 분담 및 진척 상황 파악 불가
- 계속적인 수정으로 프로그램 구조가 나빠져 수정이 매우 어려워짐

---

## 04. 선형 순차적 모델 (Waterfall Model)

> 별칭: Linear Sequential 모델, Classic Life Cycle

### 개요
- 가장 오래되고 널리 사용된 고전적 모델
- **계획 → 요구 분석 → 설계 → 구현 → 테스트 → 유지보수** 순으로 진행
- 각 단계마다 **검증(검증)** 수행

### 장점
- 관리가 용이
- **체계적인 문서화** 가능
- 요구사항의 변화가 적은 프로젝트에 적합

### 단점
- 각 단계는 앞 단계가 **완료**되어야만 수행 가능
- 각 단계의 결과물이 완벽해야 다음 단계에 오류를 넘기지 않음
- 사용자가 중간에 **가시적인 결과를 볼 수 없음**

---

## 05. V 모델

### 개요
- **폭포수 모델 + 테스트 단계 추가 확장**
- 폭포수 모델이 산출물 중심이라면, V 모델은 **각 개발 단계를 검증하는 데 초점**

### 구조
```
요구 분석 ─────────────────────── 시스템 테스트 → 인수 테스트
    ↓         (요구 분석 검증)            ↑
아키텍처 설계 ──────────────── 통합 테스트
    ↓         (인터페이스 검증)       ↑
  모듈 설계 ──────────── 단위 테스트
    ↓       (모듈 검증)     ↑
           구현 ──────────
```

## 06. 진화적 프로세스 모델 (Evolutionary Process Model)

### 등장 배경
- 폭포수 모델의 한계를 보완하기 위해 등장
- 대표 모델: **프로토타입(Prototype) 모델**

### 프로토타입이란?
- 대량 생산에 앞서 미리 제작해보는 **원형 또는 시제품**
- 소프트웨어에서는 완전한 SW를 만들기 전에 사용자 요구를 받아 모형을 만들고, **사용자와 의사소통하는 도구**로 활용

### 프로토타입 모델의 개발 생명주기
```
요구 수정 → 빠른 설계 → 프로토타입 개발 → 고객 평가 → 프로토타입 조정 → 구현
```

### 종류
| 종류 | 특징 |
|------|------|
| **실험적 프로토타입** | 요구 분석 후 프로토타입 개발 → 고객 평가 → 만족 시 정식 개발(분석→설계→구현) |
| **진화적 프로토타입** | 프로토타입을 점진적으로 발전시켜 최종 제품으로 완성 |

### 프로토타입 개발 단계
1. **요구사항 정의 및 분석**: 1차 개략적 요구 → n차 반복 → 최종 프로토타입
2. **프로토타입 설계**: 사용자 인터페이스 중심의 입출력 화면 설계
3. **프로토타입 개발**: 완제품이 아닌, 사용자 요구 항목 확인용 모형

## 09. 통합 프로세스 모델 (UP: Unified Process)

### 등장 배경
- 폭포수 모델의 문제점 → **반복적 개발 방법**으로 해결

### 반복적 개발 방법
- 전체 개발을 여러 번의 반복(R→A→D→C→T→M)으로 나누어 진행
- 각 반복마다 요구 사항 정의, 분석, 설계, 구현, 테스트, 유지보수를 수행

### UP 모델의 4단계
| 단계 | 영문 | 주요 내용 |
|------|------|-----------|
| **도입** | Inception | 프로젝트 범위 정의, 비즈니스 모델링 집중 |
| **구체화** | Elaboration | 요구사항 정의, 분석 및 설계 집중 |
| **구축** | Construction | 구현, 테스트 집중 |
| **전이** | Transition | 배포, 사용자 인수 |

### 공통 작업 (전 단계에 걸쳐 수행)
- 형상(변화) 관리
- 프로젝트 관리
- 환경 점검

### 비즈니스 모델링
- 시스템이 운영될 **비즈니스 환경을 이해하고 분석**하는 핵심 작업
- 프로젝트 초기(도입 및 구체화 단계)에 집중
- **BPMN** (Business Process Model and Notation): 업무 흐름을 시각화·표준화하는 그래픽 표기법

## 10. 애자일 프로세스 모델 (Agile Process Model)

### 개요
- **'날렵한', '민첩한'** 이라는 뜻
- 고객의 요구에 **민첩하게 대응**하고 그때그때 주어지는 문제를 풀어나가는 방법론

### 애자일 선언문 (4가지 기본 가치)
| 중시하지 않음 | 중시함 |
|--------------|--------|
| 프로세스와 도구 중심 | **개개인과의 상호 소통** |
| 문서 중심 | **실행 가능한 소프트웨어** |
| 계약과 협상 중심 | **고객과의 협력** |
| 계획 중심 | **변화에 대한 민첩한 대응** |

### 개발 방법
- **반복적인 개발**을 통한 잦은 출시 목표
```
프로토타입 개발 → 사용자 확인 → 일부 기능 사용
```

### 스크럼 (Scrum)
- 팀의 **개선과 프로젝트 관리**를 위한 애자일 방법론
- 경험적 관리 기법 중 하나
- 구체적인 프로세스보다 **팀 운영 방식(지침)**에 집중

### 스크럼 진행 과정
```
① 제품 기능 목록(백로그) 작성
② 스프린트 계획 회의
③ 스프린트 수행 (1~4주, 매일 일일 스크럼 회의)
④ 스프린트 개발 완료 → 최종 제품
⑤ 스프린트 검토 회의 + 스프린트 회고
```

> **스크럼 철학**: "팀원들이 럭비의 스크럼처럼 똘똘 뭉쳐서(Scrum), 짧은 구간을 전력 질주(Sprint)하며 목표를 달성한다"

## 모델 비교 요약

| 모델 | 특징 | 적합한 상황 |
|------|------|------------|
| 주먹구구식 | 프로세스 없음, 코딩→수정 반복 | 소규모, 단기 프로젝트 |
| 폭포수(Waterfall) | 순차적, 단계별 문서화 | 요구사항이 명확하고 변화 적은 경우 |
| V 모델 | 폭포수 + 각 단계별 테스트 검증 | 품질 검증이 중요한 경우 |
| 프로토타입 | 시제품으로 요구사항 확인 반복 | 요구사항이 불명확한 경우 |
| 통합 프로세스(UP) | 반복적 개발, 4단계 구조 | 중대형 객체지향 프로젝트 |
| 애자일(스크럼) | 민첩한 반복 개발, 고객 소통 중심 | 변화가 잦고 빠른 출시 필요 시 |
